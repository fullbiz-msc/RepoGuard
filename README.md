# RepoGuard — ранняя версия

Локальный помощник для первичной проверки исходников. Работает без Codex, Claude, подписки, API-ключей, сети и Python-пакетов. Требуется Python 3.10 или новее. Лицензия MIT.

Это небольшой проверяемый стартовый инструмент, а не полноценная замена анализаторам потоков данных, пентесту или экспертизе безопасности. Он ищет восемь типов опасных конструкций и возможные секреты. Покрытие синтаксиса ограничено, возможны ложные срабатывания и пропуски. Логику платежей и разграничения доступа сканер автоматически не проверяет.

## Запуск без ИИ

Скачайте этот репозиторий. Из его каталога выполните:

```sh
python3 project_audit.py /absolute/path/to/project --output /absolute/path/to/new-audit-report
```

Каталог отчёта должен быть новым и находиться вне проверяемого проекта. Скрипт создаёт в нём `SECURITY-REPORT.md` и `report.json`. Существующий каталог не перезаписывается. Код возврата: `0` — кандидатов и ошибок нет; `1` — есть кандидаты; `2` — ошибка или неполная проверка. Код `0` не означает, что проект безопасен.

Сканер не запускает проверяемый код, тесты, установку зависимостей и сетевые запросы. Не исправляет файлы. Не следует по символическим ссылкам. Ограничивает чтение каждого файла одним мегабайтом и перечисляет пропуски. Читает UTF-8. Пропускает зависимости и сборочные каталоги; их безопасность не считается проверенной. В JSON сохраняет хеши прочитанных файлов, но не строки исходников и значения секретов. Пути файлов также могут содержать конфиденциальные сведения: проверьте отчёт перед публикацией.

Для технической защиты запускайте на неизменяемой копии проекта с доступом ОС только для чтения, а каталог отчётов оставляйте доступным для записи. Скрипт не устанавливает эти права сам и не защищает от всех гонок подмены каталогов во время чтения. Не проверяйте одновременно изменяющийся недоверенный каталог с повышенными правами.

## Подтверждение чтения env

Агент сначала проверяет код и использование конфигурации без открытия env. Если нужно содержимое `.env`, `.env.*`, `*.env` или известного секретного конфига, он объясняет цель и запрашивает явное согласие на конкретные пути. Пока ответа нет, продолжает остальной аудит; при отказе отмечает «конфигурация не проверена — чтение не разрешено». Общая команда «проверь проект» не является таким согласием. Значения секретов не включаются в отчёт; разрешение на чтение не означает разрешения отправлять их внешним сервисам.

Самостоятельный `project_audit.py` при обычном интерактивном запуске спрашивает перед чтением **каждого** env-файла. Только `да`/`д`/`yes`/`y` разрешают чтение; пустой или другой ответ означает отказ. Имена `.env.example`, `.ENV.local` и `service.env` тоже защищены. Агент не должен отвечать на запрос за пользователя.

При запуске без интерактивного терминала сканер не может получить подтверждение: env-файлы не открываются, пути попадают в список непроверенного, а итог показывает число `env без согласия`. Код завершения `0` по-прежнему означает только отсутствие найденных кандидатов и ошибок, а не полный охват или безопасность. Это ограничение касается env-файлов; универсальное распознавание всех секретных конфигов произвольного проекта сканер не обещает.

Для встраивания в собственный интерфейс функция `scan` принимает `env_approval(path)`: интерфейс обязан получить реальное согласие пользователя на каждый путь и вернуть строго `True` только после него. Без callback env не читается. Callback — механизм подключения интерфейса, а не доказательство согласия и не защита от произвольного кода.

## Что проверяется

| Правило | Что вызывает кандидата |
| --- | --- |
| SECRET | Некоторые форматы ключей, заголовки закрытых ключей и строковые присваивания с именами секретов |
| TLS-VERIFY | `verify=False`, `rejectUnauthorized: false` |
| JWT-VERIFY | Некоторые формы отключения проверки подписи |
| SHELL | `shell=True` |
| DESERIALIZE | `pickle.load` / `pickle.loads` |
| EVAL | Вызов `eval` |
| SQL-DYNAMIC | f-string непосредственно в `execute` / `executemany` |
| DEBUG | `debug=True` |
| DOM-HTML | Присваивание `innerHTML` |

Это лексические правила, а не доказательство эксплуатации. Например, фиксированная команда с `shell=True` не обязательно содержит инъекцию. Многострочная конструкция может быть пропущена. Комментарии, примеры и строковые литералы могут давать ложные срабатывания. Потенциальная серьёзность описывает последствия при выполнении условий, которые должен проверить человек или ИИ.

## Более глубокий аудит с ИИ

В репозитории два самостоятельных файла инструкций:

- `codex/security-readonly-audit/SKILL.md` — для Codex.
- `claude/security-readonly-audit/SKILL.md` — для Claude с доступом к исходникам.

Они намеренно содержат одинаковые основные требования, чтобы критерии качества и ограничения не зависели от поставщика. Файлы не предоставляют доступ к моделям и не оплачивают его. Использование локального сканера от них не зависит.

Можно передать содержимое нужного файла как инструкцию агенту вместе с доступом к проекту. Для установки как навыка используйте механизм навыков своей среды. Простое размещение файла рядом с проектом не гарантирует автоматической загрузки. Доступность файлов и ограничения среды нужно проверить самостоятельно.

Пример задания агенту:

> Примени security-readonly-audit к проекту PATH. Исходники только читай. Отчёт сохрани в REPORT_DIRECTORY вне проекта. Прилагаю report.json локального сканера: проверь кандидатов по коду и отдельно изучи права доступа, защиту данных, платежи и сценарии мошенничества. Не запускай код и запросы к сервисам.

Инструкции требуют доказательств с файлами и строками, отделения предположений от подтверждённых путей, маскирования секретов и сохранения пробелов покрытия. Они запрещают исправления, выполнение проекта и активные атаки. Для реального ограничения записи используйте права ОС/песочницу. Качество ИИ-аудита зависит от модели, доступных файлов и контекста; инструкции не гарантируют обнаружения всех проблем.

## Покрытие полного ИИ-аудита: 20 проверок

Оба скилла содержат самостоятельный файл `references/security-checklist.md`: вход и сессии, API-ключи, БД, HTTPS, пароли, серверная валидация, XSS, админка, параметризованные запросы, окружение, лимиты, CORS, заголовки, cookies/CSRF, файлы, платежи, production/debug, зависимости, история Git и доказательства/план проверки.

В полном отчёте агент должен отразить все 20 областей: защита подтверждена в проверенном охвате / найден дефект / не проверено / неприменимо с причиной. Отсутствие конфигурации или доступа к среде не считается успешной проверкой. Копируйте каталог скилла целиком вместе с `references/`, а не только SKILL.md.

Это расширение инструкций ИИ, а не новые возможности `project_audit.py`: локальный сканер по-прежнему выполняет только описанные выше лексические проверки и не выдаёт заключение по всем 20 областям.

RepoGuard не применяет исправления, не обновляет зависимости, не отзывает ключи и не запускает тесты или атаки. Явная команда на конкретное исправление — отдельная задача реализации вне режима аудита, без автоматического разрешения остальных рекомендаций и деплоя.

## Проверка разработки

```sh
python3 -m unittest discover -s tests -v
```

Тесты используют временные синтетические исходники: проверяют обнаружение кандидатов, отсутствие выполнения кода и изменения файла, сокрытие секрета, параметризованный SQL, пропуск символических ссылок и больших файлов, обработку неверной кодировки. Это не измерение полноты обнаружения реальных уязвимостей.

## Публикация и сообщения о проблемах

Перед публикацией отчёта удалите персональные данные, внутренние пути и сведения, позволяющие атаковать ещё не исправленный сервис. Не публикуйте реальные секреты и закрытые исходники. Если проблема относится к чужому проекту, используйте его закрытый канал сообщения об уязвимостях. Для ошибок этого инструмента достаточно минимального синтетического примера без секретов.

Это ранняя версия проекта. Перед стабильным релизом нужны независимая проверка, более широкий набор учебных проектов и измерение ложных срабатываний и пропусков.
